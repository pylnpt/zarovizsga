a) Webprogramozás II — PHP

Hivatalos kérdés: 1. A dinamikus weboldalak jellemzői, összehasonlításuk a statikus tartalmakkal 2. A PHP nyelv jellemzői, használatának feltételei a webfejlesztés során 3. Kliens és szerver oldali infrastruktúra a PHP futtatásához 4. A PHP típusrendszere: típusok, konstansok, változók a PHP-ban 5. A HTML és a PHP kapcsolata 6. Modulszerkezet kialakítása, a forráskód újrahasznosításának lehetőségei 7. Adatcsere a kliens és szerver oldal között 8. Biztonsági kérdések 9. Munkafolyamatok és sütik kezelése

Dinamikus vs statikus weboldalak

Statikus weboldal: - A szerver mindig ugyanazt a HTML-t küldi vissza - Tartalom közvetlenül a fájlrendszerben (.html fájlok) - Gyors, egyszerű - Nem személyre szabható, nem interaktív

Dinamikus weboldal: - A szerver futás közben generálja az oldalt (felhasználó, adatbázis, paraméterek alapján) - PHP, Python, Node.js, ASP.NET stb. szerver-oldali kód - Bejelentkezés, e-shop, fórum, közösségi oldal - Komplexebb, lassabb (de cache-elhető)

PHP nyelv jellemzői

PHP (PHP: Hypertext Preprocessor): szerver oldali, dinamikusan típusos, interpretált programozási nyelv. Eredetileg webfejlesztésre.

Jellemzői: - Dinamikusan típusos — futás közben dől el a típus - C-szerű szintaxis - Beágyazható HTML-be közvetlenül - Nagy közösség, sok keretrendszer (Laravel, Symfony) - Beépített webhez kapcsolódó függvények (cookie, session, DB, fájl) - WordPress, Drupal, Magento mind PHP-ban íródott

Használat feltételei: - A szerveren legyen PHP interpreter - Webszerver (Apache, Nginx) konfigurálva legyen PHP-feldolgozásra (gyakran FastCGI/PHP-FPM) - Adatbázis-kapcsolat (általában MySQL/MariaDB) — opcionális

Kliens és szerver oldali infrastruktúra

Kliens oldal (böngészőben fut): - HTML (struktúra) - CSS (kinézet) - JavaScript (interaktivitás)

Szerver oldal (szerveren fut): - Webszerver (Apache, Nginx, IIS) - PHP interpreter (vagy másik szerver-oldali nyelv) - Adatbázis (MySQL, PostgreSQL) - Cache (Redis, Memcached) - A LAMP stack: Linux + Apache + MySQL + PHP

Életciklus egy PHP kérésnél: 1. Böngésző küld HTTP kérést a szervernek (pl. GET /index.php) 2. Webszerver fogadja, PHP fájl esetén a PHP interpreternek továbbítja 3. PHP interpreter értelmezi a fájlt, futtatja a kódot 4. Eredmény (általában HTML) visszamegy a kliensnek 5. Böngésző megjeleníti

PHP típusrendszere

Skalár típusok: - int — egész - float (vagy double) — lebegőpontos - string — szöveg - bool — logikai

Összetett: - array — szám- vagy string-kulcsos asszociatív tömb (ami egyben lista is) - object — osztály példánya - callable — függvényre hivatkozás

Speciális: - null — érték hiánya - resource — külső erőforrás (fájl, DB kapcsolat)

Dinamikus típusosság: változó típusa futás közben változhat.

$x = 5;       // int
$x = "öt";    // string — ugyanaz a változó

Konstansok és változók

Változó: $ jellel kezdődik.

$nev = "Anna";
$eletkor = 25;

Konstans: define() függvénnyel vagy const kulcsszóval.

define('PI', 3.14);
const VERSION = '1.0';
echo PI;

Predefinált változók (superglobálisok): - $_GET — URL paraméterek - $_POST — form mezők - $_REQUEST — GET + POST + COOKIE - $_SESSION — session adatok - $_COOKIE — sütik - $_FILES — feltöltött fájlok - $_SERVER — szerver és kliens info

HTML és PHP kapcsolata

PHP közvetlenül HTML-be ágyazható <?php ... ?> blokkokkal.

<!DOCTYPE html>
<html>
<body>
    <h1>Hello, <?php echo $nev; ?>!</h1>
    <?php if ($eletkor >= 18): ?>
        <p>Nagykorú vagy.</p>
    <?php else: ?>
        <p>Kiskorú vagy.</p>
    <?php endif; ?>
</body>
</html>

A PHP feldolgozza a <?php ?> részeket, a többit változatlanul küldi a kliensnek.

Modulszerkezet, kód-újrahasznosítás

include 'fajl.php'; — egy másik PHP fájl tartalmát beemeli. Ha hiányzik → figyelmeztetés.

require 'fajl.php'; — ugyanaz, de hiányzó fájl esetén fatális hiba (állj).

include_once / require_once — csak egyszer, akkor sem ha többször hívnánk (osztálydefinícióknál).

Strukturálás: - Konfiguráció külön fájlban (config.php) - Adatbázis-kapcsolat külön fájlban - Header / footer komponensek - Osztályok külön fájlban (PSR-4 autoloading)

Modern megközelítés: PSR-4 autoloading — névtér alapján automatikusan tölt be osztályfájlokat.

spl_autoload_register(function ($class) {
    include "classes/$class.php";
});

Adatcsere a kliens és szerver között

Form (HTML):

<form method="POST" action="kezelo.php">
    <input name="nev" />
    <input type="submit" />
</form>

PHP oldal:

$nev = $_POST['nev'];
echo "Szia, $nev!";

HTTP módszerek: - GET: URL-ben (látható, könyvjelzőzhető). Adatlekérdezéshez. $_GET-tel. - POST: body-ban (nem látszik az URL-ben, nem cache-elt). Adat-módosításhoz. $_POST-tal.

AJAX: JavaScript-tel a kliens aszinkron HTTP-kérést küld a szervernek — nem kell az egész oldalt újratölteni.

JSON: modern szerver-kliens kommunikáció (REST API).

header('Content-Type: application/json');
echo json_encode(['nev' => 'Anna', 'eletkor' => 25]);

Biztonsági kérdések

SQL Injection: ha a felhasználói input közvetlenül SQL-be megy.

// ROSSZ:
$id = $_GET['id'];
$sql = "SELECT * FROM users WHERE id = $id";

// JÓ — prepared statement:
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
$stmt->execute([$_GET['id']]);

XSS (Cross-Site Scripting): ha kliens input visszaíródik a HTML-be JavaScript-tel.

// ROSSZ:
echo $_GET['nev'];

// JÓ:
echo htmlspecialchars($_GET['nev'], ENT_QUOTES, 'UTF-8');

CSRF (Cross-Site Request Forgery): valaki más nevében küldenek kérést. - Védelem: CSRF token form-ban + ellenőrzés szerveren - SameSite cookie attribútum

Egyéb: - Jelszó hashelés: soha tisztán! password_hash() és password_verify() (bcrypt/argon2) - HTTPS mindenhol - Input validáció szerver oldalon (a kliens validációba ne bízzunk meg) - File upload: ellenőrizd a típust, ne futtatható mappába mentsd

Munkafolyamatok (session) és sütik

Cookie (süti): a szerver kis adatdarabot tárol a kliens böngészőjében, és minden kéréssel visszaküldi.

setcookie("user", "anna", time() + 3600);  // 1 órás
echo $_COOKIE["user"];
  • A kliensen tárolódik — limit ~4 KB, manipulálható
  • HttpOnly flag: JavaScriptből nem érhető el (XSS védelem)
  • Secure flag: csak HTTPS-en megy át
  • SameSite: CSRF védelem

Session: szerver oldali állapot-tárolás. A kliens csak egy session ID-t tárol cookie-ban (vagy URL-ben), az adat a szerveren van.

session_start();
$_SESSION['user_id'] = 42;
echo $_SESSION['user_id'];
  • Nem manipulálható a klienstől (csak a session ID lopható)
  • Bejelentkezett állapot megőrzése, kosár tartalma stb.

Tervezési minták szerepe

Tervezési minta (design pattern): újrahasznosítható megoldás egy gyakori tervezési problémára. Nem konkrét kód, hanem séma — sok helyzetben adaptálható.

Előnyök: - Közös szókincs — fejlesztők gyorsabban értik egymást - Bevált megoldások — sokan tesztelték - Karbantarthatóság - Bővíthetőség

A Gang of Four (GoF) könyv (1994) 23 mintát rendszerezett.

Tervezési minták osztályozása (GoF)

1. Létrehozási (Creational) — hogyan készítünk objektumokat: - Egyke (Singleton) — egyetlen példány - Gyár-metódus (Factory Method) - Absztrakt gyár (Abstract Factory) - Építő (Builder) - Prototípus (Prototype)

2. Szerkezeti (Structural) — hogyan állítunk össze osztályokat/objektumokat: - Adapter — illeszt két inkompatibilis interfészt - Díszítő (Decorator) — futás közben bővít funkciókkal - Proxy — helyettesít, vezérli a hozzáférést - Híd (Bridge), Összetétel (Composite), Légyszúly (Flyweight), Homlokzat (Facade)

3. Viselkedési (Behavioral) — hogyan kommunikálnak az objektumok: - Stratégia (Strategy) — algoritmus-családot kicserélhetővé tesz - Sablon metódus (Template Method) — algoritmus váza, lépéseket leszármazottak adják - Megfigyelő (Observer) — esemény-értesítés - Iterátor, Parancs (Command), Állapot (State), Felelősséglánc (Chain of Responsibility), stb.

Stratégia vs Sablon metódus

Stratégia (Strategy): egy interface, több implementáció. A kliens futás közben választ köztük — kompozícióval (delegálás).

interface IRendezo {
    void Rendezz(int[] arr);
}

class Buborek : IRendezo { ... }
class Quicksort : IRendezo { ... }

class Kontextus {
    private IRendezo _strat;
    public Kontextus(IRendezo s) { _strat = s; }
    public void Csinald(int[] arr) { _strat.Rendezz(arr); }
}

Sablon metódus (Template Method): absztrakt osztály egy megírt vázzal (template method), aminek néhány lépését absztrakt metódusként hagyja — a leszármazott implementálja. Öröklődéssel.

abstract class Vaz {
    public void Csinald() {     // template method
        Lepes1();
        Lepes2();
        Lepes3();  // absztrakt
    }
    private void Lepes1() { ... }
    private void Lepes2() { ... }
    protected abstract void Lepes3();
}

class Konkret : Vaz {
    protected override void Lepes3() { ... }
}

Összehasonlítás:

Stratégia Sablon metódus
Mechanizmus Kompozíció Öröklődés
Variáció Cserélhető objektumok Felülírt metódusok
Időpont Futás közben váltható Fordításkor rögzítve
Algoritmus szerkezete Teljes a stratégiában Vázat ad, részleteket bízza

Megfigyelő (Observer)

Egy alany (Subject) objektum állapotváltozásairól értesít minden megfigyelőt (Observer), anélkül, hogy ezek konkrét típusát ismerné.

interface IObserver { void Update(string esemeny); }

class Subject {
    private List<IObserver> obs = new();
    public void Subscribe(IObserver o) { obs.Add(o); }
    public void Notify(string ev) {
        foreach (var o in obs) o.Update(ev);
    }
}

Fajtái: - Push: az alany az adatot is átadja a Notify-ban - Pull: az alany csak értesít, az observer lekérdezi szükség szerint

Felhasználás: GUI eseménykezelés, MVC, pub-sub minta, .NET event-jei.

Egyéb tervezési minták

Egyke (Singleton):

public sealed class Logger {
    private static Logger _instance;
    private Logger() {}
    public static Logger Instance => _instance ??= new Logger();
}

Csak egy példány a teljes alkalmazásban. Logger, konfiguráció, DB kapcsolat-pool.

Díszítő (Decorator): objektumot körbeveszünk egy másikkal, ami kibővíti a viselkedését. Pl. stream tömörített/titkosított rétegek.

Adapter: két inkompatibilis interface-t illeszt össze (pl. régi API új API-hoz).

Iterátor: kollekció bejárási mechanizmusát különválasztja. C#-ban beépített (IEnumerable<T>, foreach).

Parancs (Command): kérést objektummá csomagolunk — undo, queue, log lehet rá.

OO tervezési alapelvek

SOLID: - S — Single Responsibility: egy osztálynak egy felelőssége legyen - O — Open/Closed (nyitva-zárt): bővítésre nyitott, módosításra zárt - L — Liskov Substitution: ős helyett mindig használható a leszármazott - I — Interface Segregation: kis, fókuszált interface-ek (ne kényszerítsünk klienst olyan metódusokra, amiket nem használ) - D — Dependency Inversion: absztrakcióktól függünk, ne konkrét osztályoktól

Nyitva-zárt alapelv bemutatása

Bővítésre nyitott, módosításra zárt. Új funkciókat tudjunk hozzátenni anélkül, hogy a meglévő (jól működő, tesztelt) kódot változtatnánk.

Megvalósítás: interface-ek és absztrakt osztályok + polimorfizmus. Egy új viselkedés = új implementáló osztály — a meglévőket nem kell hozzányúlni.

Példa — ROSSZ (módosításra nyitott):

class Calc {
    public double Calc(string op, double a, double b) {
        if (op == "+") return a + b;
        if (op == "-") return a - b;
        // új művelet → ezt a metódust módosítani kell
    }
}

Példa — JÓ (nyitva-zárt):

interface IOp { double Apply(double a, double b); }
class Add : IOp { ... }
class Sub : IOp { ... }
// új művelet → új osztály, a Calc nem változik

GOF1 és GOF2 alapelvek

GOF1 — "Programozz interfészre, ne implementációra" - A változókat / paraméterezést interface típusra írjuk, ne a konkrét osztályra - Lehetővé teszi az implementáció későbbi cseréjét anélkül, hogy a klienskódot módosítani kellene

// rossz
List<int> lista = new List<int>();

// jó
IList<int> lista = new List<int>();  // vagy IEnumerable, ICollection

GOF2 — "Részesítsd előnyben a kompozíciót az öröklődéssel szemben" - Az öröklődés erős kapcsolat — futás közben nem változtatható - A kompozíció (egy másik objektum tartása) rugalmasabb — futás közben cserélhető - Pl. a Stratégia minta kompozíción alapul, és sokszor jobb, mint az öröklődéssel megoldás

Egyéb alapelvek

  • DRY (Don't Repeat Yourself): ne ismételj kódot — egy logikának egy helyen kell lennie
  • KISS (Keep It Simple, Stupid): a legegyszerűbb működő megoldás a legjobb
  • YAGNI (You Aren't Gonna Need It): csak azt írd meg, amire most kell — ne tervezd túl
  • Demeter törvénye: csak a közvetlen szomszédoknak küldj üzenetet ("ne beszélj idegenekkel")

Jól bevált módszerek (best practices)

TDD (Test-Driven Development):

3 lépés (Red-Green-Refactor): 1. Red: írj egy tesztet, ami megbukik (a funkció még nincs) 2. Green: írj annyi kódot, hogy a teszt átmenjen — minimális megoldás 3. Refactor: szépítsd a kódot, miközben a tesztek átmennek

Előnyök: - Automatikusan lefedett a kód tesztekkel - A kód tesztelhető szerkezetű lesz (mert úgy lett tervezve) - Korai visszajelzés — hibák hamar kiderülnek - Refactor-bátorság — biztosabbnak érzed magad

Egyéb jól bevált módszerek

  • Code Review: minden kódot átnéz egy másik fejlesztő (PR-kezelés)
  • Continuous Integration (CI): minden commitnál automatikus build + teszt
  • Continuous Deployment (CD): zöld buildek automatikusan élesre kerülnek
  • Páros programozás: ketten egy gépen
  • Refactoring: a meglévő kód javítása a viselkedés megőrzésével
  • Naming conventions: beszédes, konzisztens változó- és metódusnevek
  • Verziókezelés (Git) — branch stratégiák (Git Flow, trunk-based)
  • Dokumentáció: kódba közvetlenül, vagy külön (README, JSDoc, doc-comment)
