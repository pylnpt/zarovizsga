a) Programozási technológiák — osztály, OOP-elvek, tervezési minták részletesen

Hivatalos kérdés: 1. Az osztály jellemzői: felület és megvalósítás, az objektum jellemzői: felület, belső állapot és viselkedés 2. Az OOP alapelvek megfogalmazása ezekkel a fogalmakkal 3. A GOF1 és a GOF2 tervezési alapelvek bemutatása 4. A stratégia részletes, illetve a viselkedési tervezési minták általános bemutatása 5. Az egyke részletes, illetve a létrehozási tervezési minták általános bemutatása 6. A díszítő részletes, illetve a szerkezeti tervezési minták általános bemutatása

Az osztály jellemzői

Az osztály két részből áll:

Felület (interface, kontraktus): - A "mit" — milyen szolgáltatások állnak rendelkezésre - Publikus metódusok, property-k szignatúrái - A többi osztály kívülről ezt látja és használja

Megvalósítás (implementation): - A "hogyan" — a felület mögötti tényleges kód - Privát mezők, segédmetódusok - A felhasználó számára rejtett, bármikor változhat

Az objektum jellemzői

Az objektum = osztály egy konkrét példánya. Három aspektussal jellemezhető:

Felület: a publikus metódusok, amikkel kívülről kommunikálunk vele. Megegyezik az osztály felületével.

Belső állapot: a privát mezők aktuális értékei — az objektum aktuális helyzete a futás közben. Két azonos osztályú objektum különböző állapotban lehet.

Viselkedés: hogyan reagál a metódushívásokra. A viselkedést a megvalósítás határozza meg, de függhet a belső állapottól (pl. üres verem pop()-jára kivételt dob).

OOP alapelvek a felület/állapot/viselkedés fogalmakkal

Egységbe zárás (encapsulation): - Az adat (belső állapot) és a rajta értelmezett műveletek (viselkedés) egy egységben (osztály) vannak - A felület közvetít kifelé — kívülről csak a felületen keresztül lehet hatni az állapotra

Adatrejtés (information hiding): - A belső állapot közvetlenül nem elérhető kívülről - Csak a publikus felületen keresztül → biztosítható, hogy az állapot mindig konzisztens (invariánsok) - Lehetővé teszi a megvalósítás cseréjét anélkül, hogy a felhasználók kódját módosítani kellene

Öröklődés (inheritance): - Új osztály örökli egy meglévő osztály felületét és megvalósítását, és kibővítheti / specializálhatja - A leszármazott automatikusan az ős minden publikus szolgáltatását nyújtja

Polimorfizmus (többalakúság): - Ugyanaz a felület-művelet különböző viselkedést mutathat az osztály konkrét típusától függően - Megvalósítás: virtual + override, késői kötés (dinamikus diszpécs) - Lehetővé teszi, hogy a kliens csak a felülettel dolgozzon, és a konkrét típus a futás idején dőljön el

GOF1 — Programozz interfészre, ne implementációra

A változók, paraméterek típusát mindig a legabsztraktabb interface-en vagy absztrakt osztályon adjuk meg, amit elég. A konkrét típus csak a példányosításnál érdekes.

// rossz
List<int> lista = new List<int>();

// jó
IList<int> lista = new List<int>();
// vagy ICollection<int>, IEnumerable<int>

Előnyök: - A konkrét implementáció később cserélhető anélkül, hogy a klienseket módosítani kellene - A tesztelés könnyebb (mock-olható az interface) - Csökken az osztályok közötti csatolás (coupling)

GOF2 — Részesítsd előnyben a kompozíciót az öröklődéssel szemben

Öröklődés (is-a): - Erős, fordításidőben rögzített kapcsolat - Az ős változása mindenki leszármazottját érinti - Nehezen változtatható a viselkedés futás közben - Egyszeres öröklődés korlátozó

Kompozíció (has-a): - Egy objektum birtokol egy másik objektumot - A birtokolt objektum futás közben cserélhető - Rugalmasabb, lazább kapcsolat

// Öröklődés - merev
class Madar : Allat { void Repul() {} }
class Pingvin : Madar { /* baj: a pingvin nem repül! */ }

// Kompozíció - rugalmas
class Madar {
    private IRepules r;
    public Madar(IRepules r) { this.r = r; }
    void Akciot() { r.Tegyel(); }
}
new Madar(new Repkedo());
new Madar(new NemRepkedo());

A Stratégia minta klasszikus alkalmazása a kompozíciónak.

Stratégia minta részletesen (viselkedési)

Probléma: sok hasonló algoritmus (pl. rendezés, fizetés módja), és futás közben szeretnénk váltani közöttük, anélkül, hogy a kliens kódját módosítanánk.

Megoldás: definiálj egy közös interfészt az algoritmusoknak, és a kliens kompozíción keresztül tartson belőle egy példányt.

public interface IRendezo {
    void Rendezz(int[] arr);
}

public class Buborek : IRendezo {
    public void Rendezz(int[] arr) { /* O(n²) */ }
}

public class Quicksort : IRendezo {
    public void Rendezz(int[] arr) { /* O(n log n) */ }
}

public class Kontextus {
    private IRendezo _strat;
    public Kontextus(IRendezo s) { _strat = s; }
    public void SetStrategy(IRendezo s) { _strat = s; }
    public void Csinald(int[] arr) {
        _strat.Rendezz(arr);
    }
}

// Használat
var k = new Kontextus(new Buborek());
k.Csinald(arr);
k.SetStrategy(new Quicksort());  // futás közben váltunk!
k.Csinald(arr);

Előny: új algoritmus = új osztály — a Kontextus változatlan. Nyitva-zárt elv teljesül.

Viselkedési tervezési minták általános bemutatása

A viselkedési minták az objektumok közötti kommunikációt és felelősség-elosztást strukturálják.

Példák: - Stratégia (Strategy) — cserélhető algoritmusok - Sablon metódus (Template Method) — algoritmus váza öröklődéssel - Megfigyelő (Observer) — esemény-értesítés - Iterátor (Iterator) — kollekció bejárása - Parancs (Command) — kérés objektumba csomagolva (undo, queue) - Állapot (State) — állapot-függő viselkedés objektumokba - Felelősséglánc (Chain of Responsibility) — kérés végigfut egy láncon, valaki kezeli - Közvetítő (Mediator) — objektumok közötti kapcsolatot egy közvetítő kezeli - Látogató (Visitor) — művelet egy objektumhierarchián

Egyke minta részletesen (létrehozási)

Probléma: szeretnénk garantálni, hogy egy osztályból csak egyetlen példány legyen az alkalmazás futása során — és bárhonnan elérhető legyen.

Megoldás:

public sealed class Logger {
    private static Logger _instance;
    private static readonly object _lock = new object();

    private Logger() { /* privát konstruktor! */ }

    public static Logger Instance {
        get {
            if (_instance == null) {
                lock (_lock) {
                    if (_instance == null) {
                        _instance = new Logger();
                    }
                }
            }
            return _instance;
        }
    }

    public void Log(string msg) { ... }
}

// Használat
Logger.Instance.Log("Üzenet");

Kulcs elemek: - Privát konstruktor — kívülről nem példányosítható - Statikus Instance property — a globális elérési pont - Lazy init + lock — szálbiztos egyszeri inicializálás (double-checked locking) - sealed — ne lehessen leszármazottal megkerülni

Modern C#:

public sealed class Logger {
    private static readonly Lazy<Logger> _instance =
        new Lazy<Logger>(() => new Logger());
    public static Logger Instance => _instance.Value;
    private Logger() { }
}

Mikor használjuk: logger, konfiguráció, DB connection pool, cache.

Mikor kerüljük: ha tesztelhetőség fontos (mocking nehéz), ha valójában csak globális változót akarunk (anti-pattern). Modernben sokszor dependency injection-nel váltjuk ki.

Létrehozási tervezési minták általános bemutatása

Az objektum-példányosítást rugalmasabbá teszik.

  • Egyke (Singleton) — egyetlen példány
  • Gyár-metódus (Factory Method) — leszármazottak döntik el, milyen konkrét típust hoznak létre
  • Absztrakt gyár (Abstract Factory) — kapcsolódó objektum-családokat hoz létre
  • Építő (Builder) — komplex objektumot lépésről lépésre épít
  • Prototípus (Prototype) — meglévő példányt klónoz

Díszítő minta részletesen (szerkezeti)

Probléma: egy objektumhoz futás közben szeretnénk plusz felelősséget rendelni, anélkül, hogy az osztály-hierarchiát módosítanánk vagy hatalmas leszármazott-fát építenénk.

Megoldás: a díszítő osztály ugyanazt az interfészt implementálja, mint a díszítendő objektum, és körbeveszi azt — előtte/utána tehet pluszt.

public interface IStream {
    void Write(string data);
}

public class FileStream : IStream {
    public void Write(string data) { /* fájlba ír */ }
}

// Díszítő alaposztály
public abstract class StreamDecorator : IStream {
    protected IStream _wrapped;
    public StreamDecorator(IStream s) { _wrapped = s; }
    public abstract void Write(string data);
}

public class CompressDecorator : StreamDecorator {
    public CompressDecorator(IStream s) : base(s) {}
    public override void Write(string data) {
        var compressed = Compress(data);
        _wrapped.Write(compressed);
    }
}

public class EncryptDecorator : StreamDecorator {
    public EncryptDecorator(IStream s) : base(s) {}
    public override void Write(string data) {
        var encrypted = Encrypt(data);
        _wrapped.Write(encrypted);
    }
}

// Használat — bármelyik kombinációban
IStream s = new EncryptDecorator(new CompressDecorator(new FileStream()));
s.Write("titkos és tömörített adat");

Előnyök: - Futás közben kombinálható a viselkedés - Nyitva-zárt — új díszítő = új osztály, a meglévők változatlanok - Több módosító kombinációja lehetséges (öröklődéssel exponenciális robbanás lenne)

A .NET Stream osztály-családja klasszikusan így működik (GZipStream, CryptoStream stb.).

Szerkezeti tervezési minták általános bemutatása

Az objektumok és osztályok összeszerelését strukturálják.

  • Adapter — két inkompatibilis interface illesztése
  • Híd (Bridge) — absztrakció és implementáció szétválasztása
  • Összetétel (Composite) — fa-szerű hierarchia, ahol a kompozit és a levél ugyanazt az interfészt nyújtja
  • Díszítő (Decorator) — futás közbeni bővítés
  • Homlokzat (Facade) — egységes, egyszerű felület egy bonyolult alrendszerhez
  • Légyszúly (Flyweight) — sok hasonló objektum hatékony tárolása megosztott állapottal
  • Proxy — helyettesít egy másik objektumot, kontrollálja a hozzáférést (cache, lazy load, biztonság)

b) Adatbázisrendszerek II — Kurzorok, triggerek, kollekciók

Hivatalos kérdés: 7. Kurzorok: implicit és explicit kurzorok kezelése, kurzorattribútumok használatának lehetősége, kurzorváltozók 8. Tranzakciókezelés, triggerek a PL/SQL nyelvben 9. Összetett adatszerkezetek (kollekciók) típusai, jellemzői, használatának lehetőségei és előnyei, hátrányai

Kurzorok

Probléma: egy SQL-utasítás eredménye gyakran több sor — ezeket egyenként szeretnénk feldolgozni.

Kurzor (cursor): a memóriában lévő környezeti terület azonosítója, ami az SQL-utasítás eredményét tartalmazza (aktív halmaz) + mutatót, hogy a sorokon belül hol járunk.

Analógia: telefonkönyvben keresés az ujjunkkal — az ujj a kurzor, ami az aktuális rekordra mutat.

Implicit kurzor

A PL/SQL automatikusan felépít egy implicit kurzort minden DML-utasításhoz és minden olyan SELECT-hez, ami pontosan egy sort ad vissza.

Attribútumai (a legutoljára végrehajtott utasításra vonatkoznak): - SQL%FOUND — TRUE, ha az INSERT/UPDATE/DELETE legalább egy sort érintett, vagy SELECT INTO visszaadott sort - SQL%NOTFOUND — TRUE, ha egyetlen sort sem érintett - SQL%ROWCOUNT — érintett sorok száma - SQL%ISOPEN — mindig FALSE (az Oracle implicit kurzort automatikusan lezárja)

Explicit kurzor

Több sort visszaadó lekérdezések eredményéhez. A programozó kezeli 4 lépésben:

1. Deklarálás:

CURSOR diak_cur IS
    SELECT id, nev FROM Diakok WHERE szul_ev > 2000;

2. Megnyitás (OPEN): - Lefuttatja a lekérdezést - Meghatározza az aktív halmazt - A kurzormutató az első rekordra áll - Újra megnyitott kurzor → CURSOR_ALREADY_OPEN kivétel

OPEN diak_cur;

3. Sorok betöltése (FETCH): - Beolvassa az aktuális sort egy változóba/rekordba - A mutatót a következő sorra állítja - Nem létező sor betöltése nem dob kivételt — %NOTFOUND lesz TRUE

FETCH diak_cur INTO v_id, v_nev;

4. Lezárás (CLOSE): - Felszabadítja az erőforrást, érvényteleníti a mutatót

CLOSE diak_cur;

Teljes ciklus:

DECLARE
    CURSOR c IS SELECT id, nev FROM Diakok;
    v_id NUMBER; v_nev VARCHAR2(50);
BEGIN
    OPEN c;
    LOOP
        FETCH c INTO v_id, v_nev;
        EXIT WHEN c%NOTFOUND;
        DBMS_OUTPUT.PUT_LINE(v_id || ': ' || v_nev);
    END LOOP;
    CLOSE c;
END;

Egyszerűsített FOR-LOOP (automatikus open/fetch/close):

FOR rec IN (SELECT id, nev FROM Diakok) LOOP
    DBMS_OUTPUT.PUT_LINE(rec.id || ': ' || rec.nev);
END LOOP;

Kurzor-attribútumok (explicit)

Csak procedurális utasításokban használhatók, SQL-ben nem.

  • %FOUND — első sor előtt NULL; sikeres FETCH után TRUE, ha nem volt sor → FALSE
  • %NOTFOUND — fordítva: sikertelen FETCH után TRUE
  • %ISOPEN — TRUE, ha a kurzor meg van nyitva
  • %ROWCOUNT — eddig betöltött sorok száma (FETCH-enként +1)

Ha az explicit kurzor nincs megnyitva, akkor %ISOPEN kivételével INVALID_CURSOR kivételt váltanak.

Kurzorváltozók (REF CURSOR)

A normál explicit kurzor statikusan kötődik egy konkrét SELECT-hez. A kurzorváltozó futás közben bármilyen kompatibilis lekérdezéshez köthető — dinamikus.

Deklarálás:

TYPE my_cur_t IS REF CURSOR [RETURN return_típus];
my_cur my_cur_t;
  • Erős (strong) ref cursor: ha van RETURN — a fordító ellenőrzi a kompatibilitást
  • Gyenge (weak) ref cursor: ha nincs RETURN — bármilyen kérdés hozzákapcsolható

Használat:

OPEN my_cur FOR SELECT id, nev FROM Diakok WHERE szul_ev > 2000;
FETCH my_cur INTO v_id, v_nev;
CLOSE my_cur;

Előny: futás közben más-más lekérdezést kapcsolhatunk hozzá, paraméterként átadható eljárásnak.

Tranzakciókezelés

Lásd 7.b részletesen — ACID, COMMIT, ROLLBACK, SAVEPOINT. PL/SQL-ben:

  • COMMIT; — véglegesít
  • ROLLBACK; vagy ROLLBACK TO SAVEPOINT sp; — visszagörget
  • SAVEPOINT sp; — köztes mentési pont

Implicit COMMIT — DDL utasítás vagy felhasználói kilépés esetén. Implicit ROLLBACK — alkalmazás rendellenes leállása esetén.

Triggerek

Trigger: automatikusan végrehajtódó kód egy esemény hatására (tábla módosulása, nézet, rendszeresemény). Az adatbázis-objektum.

Jellemzők: - Megírható PL/SQL-ben, vagy Java/C-ben - Felhasználói rétegen átlátszó — a felhasználó nem hívja, automatikusan fut - Nem lehet kihagyni — speciális tárolt eljárás - Táblához vagy eseményhez kötődik - A tábla, amelyhez kötődik, az INSERT/UPDATE/DELETE után fut le

Trigger típusai:

Sorszintű (FOR EACH ROW): minden érintett sorra egyszer fut. DELETE esetén minden törölt sor aktivál.

Utasításszintű: egyszer fut le az utasításra, függetlenül attól, hány sort érintett.

BEFORE / AFTER: - BEFORE: a hozzákapcsolt utasítás előtt fut - AFTER: utána fut Mindkettő lehet sor- vagy utasításszintű.

INSTEAD OF: a hozzákapcsolt utasítás helyett fut le. Csak sorszintű, csak nézeteken.

Rendszer-triggerek: adatbázis-eseményekre (indítás, leállítás, login, logout, DDL).

Szintaxis:

CREATE [OR REPLACE] TRIGGER trig_name
{BEFORE | AFTER | INSTEAD OF}
{INSERT | UPDATE | DELETE} [OR ...]
ON tabla_nev
[FOR EACH ROW]
[WHEN (feltétel)]
BEGIN
    -- PL/SQL kód
    -- :NEW.oszlop, :OLD.oszlop a sor-szintű triggerekben
END;

Felhasználási példák: - Naplózás (audit): ki, mit, mikor módosított - Integritási megszorítások összetett esetekben - Származtatott értékek automatikus frissítése - Üzleti szabályok kikényszerítése (pl. nem lehet hétvégén rendelni)

Korlátok: sok memóriát/időt igényelhet, túlhasználata teljesítményproblémát okoz, eldugott logika nehezíti a hibakeresést.

Kollekciók — összetett adatszerkezetek

Kollekció: azonos típusú adatelemek rendezett együttese, minden elemnek egyedi indexe van. Paraméterként átadhatók — táblák oszlopai mozgathatók az alkalmazás és az adatbázis között.

3 típus: asszociatív tömb, beágyazott tábla, dinamikus tömb (VARRAY).

Asszociatív tömb (associative array)

  • Hash-tábla struktúra
  • Index lehet tetszőleges egész vagy string
  • Indexnek nincsenek határai (negatív is)
  • Deklarálható PL/SQL blokkban, alprogramban, csomagban
  • Csak PL/SQL programokban használható (adatbázis oszlop típusa nem lehet)
TYPE szam_arr IS TABLE OF NUMBER INDEX BY VARCHAR2(20);
arr szam_arr;
BEGIN
    arr('alma') := 10;
    arr('körte') := 20;
END;

Beágyazott tábla (nested table)

  • Index alsó határa: 1 (nincs felső határ)
  • Deklarálható PL/SQL-ben vagy adatbázis-objektumként (CREATE TYPE)
  • Adatbázis oszlop típusa is lehet (pl. Ugyfel.konyvek)
  • Az elemek szétszórtan helyezkednek el, lehetnek lyukak
  • Új elem tetszőleges indexű helyre vihető be, bármely törölhető
TYPE neptab IS TABLE OF VARCHAR2(50);
nevek neptab := neptab('Anna', 'Béla', 'Cili');

Dinamikus tömb (VARRAY)

  • Index alsó határa: 1
  • Maximális méret kötelezően megadandó deklarációkor
  • Adatbázis oszlop típusa lehet (pl. Konyv.szerzok)
  • Bővíthető új elemekkel, de a meglévők csak cserélhetők, nem törölhetők
  • Az elemek folytonosan helyezkednek el a kisebb indextől kezdve
TYPE szerzok_t IS VARRAY(5) OF VARCHAR2(50);
sz szerzok_t := szerzok_t('Tolkien', 'Lewis');

Összehasonlító táblázat

Asszociatív tömb Beágyazott tábla Dinamikus tömb (VARRAY)
Index típusa int vagy string int (≥1) int (1..max)
Index határa nincs nincs felső rögzített max
DB oszlop? nem igen igen
Lyukak lehetnek lehetnek nem (folytonos)
Méret kötött nem nem igen
Törölhető elem igen igen nem

Előnyök: táblák tartalmának hatékony mozgatása alkalmazás és DB között, batch művelet-műveletek (FORALL, BULK COLLECT).

Hátrányok: memóriaigény nagyobb adathalmaznál; tervezésnél el kell dönteni, melyiket választjuk.
